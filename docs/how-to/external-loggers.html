Connect External Loggers

Send contacts from N1MM Logger+, WSJT-X, JTDX, and fldigi straight into FD Commander.

How-To Guides › External Loggers
Logging · Optional

Your operators already know their favorite logging programs, and there's no reason to make them give those up for the weekend. FD Commander can listen on the local network for contacts sent by N1MM Logger+, WSJT-X, JTDX, fldigi, and anything else that sends ADIF over UDP. Each contact lands in the log a moment after the operator saves it, where it counts toward the score, gets checked for dupes, and shows up on the dashboards.

This guide walks through one logging PC from start to finish. Plan on about fifteen minutes for the first PC and a few minutes for each one after that.

Before You Start

  • FD Commander is running on your field network with a fixed IP address. If you haven't set that up yet, start with Set Up a LAN for Field Operations. The examples below use 192.168.1.50 as the server address.
  • Your event exists. Listeners attach to the current event, which is the active one or, if none is active yet, the next upcoming one. Create it first with First Event Setup.
  • You can sign in as a System Administrator or Event Manager. The External Loggers page requires the permission to import contacts, and those two roles have it by default.
  • The logging PCs are on the same network as the server. A guest Wi-Fi network with client isolation turned on will quietly drop the traffic.
Private networks only

UDP has no authentication. Anyone who can reach these ports can send contacts into your log. Only turn the listeners on when FD Commander is on a private, firewalled network, and never on a server that is reachable from the internet.

How It Works

Each logging program sends a small UDP packet to the server every time a contact is logged. FD Commander runs a separate listener for each kind of program, and each listener has its own port:

Logging programListenerDefault portStation is matched by
N1MM Logger+N1MM Logger+12060The PC's computer (NetBIOS) name
WSJT-X, JTDXWSJTX / JTDX2237The station callsign
fldigi and other ADIF sendersUDP ADIF (fldigi, etc.)2238The station callsign

When a contact arrives, FD Commander works out which station it came from, who was operating, and which band and mode were in use. It then opens an operating session for that station automatically, so the station shows up as Occupied on the Log Contact page just as if someone had signed in through the browser. A session closes on its own after about 30 minutes without a new contact.

One path per contact

Some stations chain programs together, such as WSJT-X or fldigi feeding N1MM Logger+. In that case, let N1MM Logger+ send the contacts and leave the other program pointed at N1MM. If both programs send the same contact to FD Commander, it arrives twice and the second copy is marked as a dupe.

Step 1: Open the Firewall on the Server

The deploy script opens the web port but not the logger ports. If your server runs UFW, check whether it's active:

$ sudo ufw status

If the status is active, open the port for each listener you plan to use:

$ sudo ufw allow 12060/udp # N1MM Logger+ $ sudo ufw allow 2237/udp # WSJT-X / JTDX $ sudo ufw allow 2238/udp # fldigi and other ADIF senders

On a server that uses firewalld instead, the equivalent is:

$ sudo firewall-cmd --permanent --add-port=12060/udp $ sudo firewall-cmd --reload

Repeat the first command with 2237 and 2238 if you use those listeners.

If neither firewall is active, there's nothing to do here. Raspberry Pi OS doesn't turn one on by default.

Running in Docker?

The included docker-compose.yml already publishes all three UDP ports. If you change a listener's port in FD Commander, set the matching N1MM_PORT, WSJTX_PORT, or UDP_ADIF_PORT value in your .env file to the same number, then run docker compose up -d so the container picks it up.

Step 2: Turn On the Listener

1 Sign in to FD Commander and open Logging > External Loggers.

2 Find the card for your logging program and flip its toggle on. The status changes from Starting listener... to Listening on port 12060 (or whichever port that listener uses), followed by packet and error counters.

3 Leave the page open. The packet counter is the quickest way to tell whether the logging PC can reach the server, and you'll use it in a moment.

The default ports work for nearly everyone. If you need a different one, turn the listener off first, since the port field is locked while the listener is switched on. Ports from 1024 to 65535 are allowed.

You don't need to babysit the listeners. If one stops unexpectedly while the External Loggers page is open, the page restarts it within a few seconds.

Step 3: Match Logging PCs to Stations

Every contact carries an identifier for where it came from. FD Commander compares that identifier with the name of each station in your event, then with each station's Hostname (NetBIOS Name) field. Neither comparison cares about capitalization. If nothing matches, FD Commander creates a new station named after the identifier, so contacts are never lost, but they may land somewhere you didn't expect. A few minutes of setup here keeps the stations tidy.

N1MM Logger+ stations

N1MM Logger+ identifies itself by the PC's computer name. To find it, open a Command Prompt on the logging PC and run:

C:\> echo %COMPUTERNAME% SHACK-PC-2

In FD Commander, open Stations, edit the station that PC will run, and enter that name in the Hostname (NetBIOS Name) field. Repeat for each N1MM Logger+ PC.

WSJT-X, JTDX, and fldigi stations

These programs identify contacts by the station callsign in the log record, which is normally your club or event callsign. That means every digital PC using the same callsign lands on the same FD Commander station. Pick the station that should receive those contacts, usually your digital station, and enter the event callsign (for example, W3XYZ) in its Hostname (NetBIOS Name) field.

Operator credit

Contacts are credited to the operator whose callsign the logging program reports. If that callsign belongs to an FD Commander user, the contact goes to them. If it doesn't, FD Commander creates a locked placeholder account for that callsign, labeled (Imported), so the contact still has an operator. Inviting your operators before the event, with their callsigns filled in, avoids a pile of placeholders.

If the logging program doesn't report an operator at all, the contact may end up with no operator, or with a placeholder for whatever callsign the program fills in by default. Each program section below shows where the operator's callsign goes, and it's worth making that part of every operator change.

Step 4: Configure the Logging Program

Follow the section for your program, then come back for Step 5. Repeat this step on every logging PC, since these settings are stored on each PC.

N1MM Logger+

1 In the Entry Window, open Config > Configure Ports, Mode Control, Audio, Other and select the Broadcast Data tab.

2 Check Radio and Contacts. Leave All Computers unchecked, since each PC will report its own contacts. In a networked N1MM setup, misconfigured stations with All Computers turned on can send contacts around in a loop.

3 Enter the server's address and port as the destination, written as 192.168.1.50:12060. To send to more than one program, separate the destinations with a space, as in 127.0.0.1:12060 192.168.1.50:12060. If your version shows a separate address box for Radio and for Contacts, fill in both.

4 Click OK. N1MM Logger+ sends a radio status packet at least every 10 seconds, so the packet counter on the External Loggers page should start climbing almost right away.

5 Make sure the PC is logging in an ARRL Field Day contest log, so the received class and section are sent in their own fields.

6 When an operator sits down, have them press Ctrl+O (or type OPON in the callsign box) and enter their own callsign. That's the callsign FD Commander uses for operator credit.

If an operator deletes a contact in N1MM Logger+, FD Commander removes it from the log too.

WSJT-X

These steps match WSJT-X 3.0. Open the settings with File > Settings (or press F2).

1 On the General tab, set My Call to your event callsign.

2 On the Advanced tab, check Special operating activity, choose ARRL Field Day, and enter your own exchange in FD Exch, such as 3A MDC. In this mode, WSJT-X logs the other station's class and section in their own fields. Without it, contacts still arrive, but they won't have a section for the section map.

3 On the Reporting tab, enter the operator's callsign in Op Call. Update it at each operator change, or contacts will be credited to the previous operator.

4 In the UDP Server group on the same tab, set UDP Server to the server's IP address (192.168.1.50) and UDP Server port number to 2237. Use the server's regular address, not a multicast group. The Outgoing interfaces field only appears for multicast addresses, so you won't see it with this setup.

5 Click OK. WSJT-X sends a heartbeat packet every 15 seconds, so the packet counter should start climbing within 15 seconds. Contacts are sent when the operator clicks OK in the Log QSO window.

WSJT-X sends to one place

The UDP Server setting holds a single address. If this PC also runs JTAlert, GridTracker, or N1MM Logger+'s WSJT-X integration, those programs expect WSJT-X's traffic as well. Either point WSJT-X at FD Commander and do without the companion program, or leave WSJT-X pointed at the companion program and have it pass contacts along. With N1MM Logger+, that means letting its broadcast carry the contacts, as described above. Some companion programs, such as GridTracker, can rebroadcast WSJT-X traffic to another port; check that program's documentation for details.

JTDX

JTDX is built on WSJT-X and sends the same UDP messages, so it uses the same WSJTX / JTDX listener on port 2237. Its UDP server settings are on the Reporting tab of its Settings window. Enter the server's address and port there, just as you would in WSJT-X.

fldigi

These steps match fldigi 4.2. Open Configure > Config Dialog.

1 On the Operator-Station page, set Station Callsign to your event callsign and Operator Callsign to the current operator's callsign.

2 On the Contests/Field Day page, fill in your class and section.

3 Go to the Logging/Cloud-UDP page. In the Broadcast UDP ADIF record group, set Address to 192.168.1.50 and Port to 2238. fldigi defaults to port 9876, so this one needs changing.

4 Click Select Fields and confirm that the callsign, date, time on, band, frequency, mode, station callsign, operator, class, and section fields are selected. They're all selected out of the box, so this is only a check.

5 Check Enable, then click TEST. The packet counter on the External Loggers page should go up by one. The test packet isn't a real contact, so Last Log Received won't change.

Other programs

Any program that can send plain ADIF records over UDP can use the UDP ADIF (fldigi, etc.) listener on port 2238. FD Commander needs at least the callsign, date, and time of each contact. Include the band or frequency, mode, station callsign, operator, class, and section for full credit and a complete log.

Step 5: Log a Test Contact

A climbing packet counter proves the network path works. A test contact proves the whole chain works.

1 Log a contact in the logging program.

2 On the External Loggers page, expand Last Log Received under that listener. You should see the callsign, band, mode, section, and QSO time.

3 Look at the badge next to it. Accepted means the contact is in the log. outside event window means the contact's time falls outside the event's start and end times, so FD Commander turned it away.

Testing before the event

Contacts are only accepted between the event's start and end times, so any test you run the week before will show outside event window. That's a good result. It means the packet made it all the way through and was read correctly, and nothing landed in your real log. Once the event starts, check that the station shows as Occupied on the Log Contact page, with the operator's callsign and the source program next to it.

Troubleshooting

The packet counter stays at zero

  • Confirm the logging PC can reach the server at all by opening FD Commander in a browser on that PC.
  • Double-check the address and port in the logging program. A typo in either one is the most common cause.
  • Check the server's firewall (Step 1). The listener can be running perfectly and still never see a packet.
  • On Docker, make sure the port in FD Commander matches the port published in .env.

The status says the process crashed

FD Commander tries to restart it automatically, and you can click Retry. If it keeps crashing, another program on the server is probably using the same port. Pick a different port for the listener and update the logging programs to match.

Packets arrive, but contacts don't

  • Check the Last Log Received badge. If it says outside event window, compare the event's start and end times with the contact's QSO time.
  • If the error counter is climbing, the server log has the details. On a server set up with the deploy script, run sudo tail -50 /var/www/fd-commander/storage/logs/laravel.log and look for "packet processing error."
  • For fldigi and other ADIF senders, make sure the callsign, date, and time fields are included. Records missing any of them are skipped.

A new station appeared with a computer name or callsign

The identifier didn't match any station's name or hostname, so FD Commander created one. Add the identifier to the Hostname (NetBIOS Name) field of the station it belongs to (Step 3). New contacts will go to the right place from then on. Contacts that already arrived stay on the station that was created for them.

Contacts are credited to a callsign marked "(Imported)"

The operator's callsign in the logging program didn't match any FD Commander user. Check for typos in N1MM Logger+'s operator login, WSJT-X's Op Call, or fldigi's Operator Callsign, and make sure the operator's FD Commander account has their callsign filled in.

WSJT-X contacts don't show up on the section map

WSJT-X only logs the class and section in their own fields when ARRL Field Day is selected under Special operating activity. Turn it on (see the WSJT-X steps above).
